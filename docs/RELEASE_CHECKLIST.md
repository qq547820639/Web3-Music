12. **`ReadError` 是一条被记下来却读不出的失败。** 权威运行 `acceptance-20260926T022643Z` 在第 17 步 98/100 停住：两个作业 `no_ready_candidates`，候选原因写作 `{'type': 'ReadError', 'message': ''}`——httpx 的传输层异常不带消息，于是数据库里"有原因"却没有任何可读内容，与上一轮修的 `error=NULL` 同族，只是这次原因是空的。`outcomes.error_signature()` 在无消息时以类型名兜底并带上 `__cause__`；媒体入库改走 `fetch_media_with_retry`，只对 `httpx.TransportError` 重试（3 次、0.5s/1.0s 退避），404、类型不对、超大、解码失败一律不重试，耗尽后报出的句子带次数与底层错误。两条极性各由单测钉住：抖动的下载必须被重试且退避在长大；内容类型错误的下载必须首发即失败且一次都不睡眠。修复后的权威运行 100/100（p50 4.09s / p95 5.33s）。
13. **界面与文档里的「角色合法名单」其实是第三、第四份副本。** `db/migrations/017_workspace_membership.sql` 开头写着角色名单「不重抄」，交给 `CHECK` 触发再翻译；同一个文件里的 `workspace_role_error(role)` 却把 `('owner','admin','creator','reviewer','viewer','billing','legal','support')` 八个名字拼了一遍，而四个函数每次调用都先跑它——所以真正决定合法性的就是这份第二名单，注释描述的不是现场的形状。本轮要给面板一个下拉列表，若直接在 JS 里再列一遍就是第四份。做法：`GET /api/workspace/members` 返回由 `pg_get_constraintdef` 现读的数组；`tests/unit/test_workspace_membership_writes.py` 用 AST 禁止 `allowed_workspace_roles()` 里出现任何字面角色名（拿一份手抄名单做反向对照，必须报）；`member_drill` 每次跑三方比对（端点 = CHECK 数组 = 校验函数集合），并且逐个名字真发一次 add，用「无此账户」这个失败原因证明角色那关过了。017 已入库、校验和锁死，因此没有去重构 plpgsql，而是把「两份表示必须一致」变成常驻断言。
14. **危险按钮的白字压在 #ff6b6b 上只有 2.78:1，axe 判 serious。** 这条一直潜伏着：`button.danger` 在两个应用的样式表里都写着 `background: var(--danger); color: #fff`，而在此之前它每次被扫到时都是 `disabled`，axe 不判禁用控件。名册面板给出的是「每行一个始终可用的『移出』」，第一次让它以启用态出现在被扫描的视图里，判据立刻红了 6 条（`browser-a11y-20260926T074554Z` 保留作发现记录）。修法：两个应用各自加一个 `--danger-solid: #b3261e`（白字实测 6.54:1），`--danger` 继续只作前景色用；并且这条比例不再等界面恰好触发——常驻用例直接按 WCAG 公式从两张样式表里解析 `button.danger` 的前景/背景并算比值，palette 再改回去会立刻红（两侧各自变异一次都开火）。
15. **中断的验收跑把探针账号留在演示工作区的名册里。** 清理原先挂在浏览器跑完之后的一行，于是 walk 中途抛异常就等于不打扫：今天两次中断留下 3 个 `a11y-*` 探针（名册里看得见，且会污染下一次跑法读到的成员数）。改为账号创建的那一刻就 `atexit.register` 清理，并逐表容错（中途退出可能留下被外键指着的一行，那属于清理噪声而不是被测性质）。钩子可达性不靠相信：用一支会在 `SystemExit` 路径上开火的对照证明 atexit 真的跑到（标记文件写成功），清理幂等重复调用无害。

16. **界面把某个元素标成 `hidden`，并不等于它不渲染。** 本轮给删除账户加「验证码输入框只在账号开了两步验证时才出现」这一条时，浏览器门禁的新断言直接判红：没开验证器的探针仍然看得见那个框。读码定位到 `services/web/styles.css:137` 与 `services/admin/styles.css:54` 的 `label { display: grid }`——`[hidden] { display: none }` 是浏览器默认样式表里的规则，任何作者样式对同一元素的 `display` 赋值都能压过它，于是「用属性隐藏」这条在本仓库里一直是假的。同一处失效还压着一个更大的：`services/web/app.js:321` 登录后执行 `$('#login').hidden = true`，而 `#login` 带着 `.login-shell`、后者是 `display: grid`（styles.css:188），所以**登录页在每一个已登录视图上都叠在应用上方**——把本轮和上一轮同一视图的截图并排看即可见（旧图顶部是整屏落地页与「登录」按钮，新图从顶栏开始）。这条不是本轮新引入的回归：门禁自己留下的 15 份报告里，`region` 违规数与扫描数几乎 1:1 增长（62 次扫描 180 个节点、88 次 324 个、96 次 348 个），说明每个视图都被扫到一遍登录表单；修完之后同一轮 96 次扫描只剩 46 个节点。修法两步：两套样式表都把属性定为最终答案（`[hidden] { display: none !important }`），并给浏览器门禁加一次全站扫描——凡带 `hidden` 的元素都要真的算不出 `display`，且带分母断言（整套扫描里一个 `hidden` 元素都没见到就判红，免得空扫描冒充干净，本轮实测 840 个元素、0 个仍渲染）。判据侧留了五支对照（`--self-test`）与一条常驻单测，各自的必开火/必不开火两侧都在。

### 已澄清（上一版记为"需属主决策"，读码 + 实测后确认不是缺口）

1. **平台 15% 服务费不是"没有分录"。** 上一版本文说它在账本里没有分录，一半说对了、一半说错了：`ledger_accounts` 里 15 个账户的 `currency` **全部是 `CREDIT`**——积分账本按 credit 计量，货币收入本就不该往这里塞；货币侧分录在 `revenue_splits`，`record_license_revenue` 为每张许可证写一对 `(workspace 8500, platform 1500)`，实测库里 6 张许可证正好 6+6 行、合计 60000bp。更硬的一层是数据库自己：`revenue_split_total_must_balance` 约束触发器要求同一 subject 的分账和恰为 10000bp，两向探针实测——成对插入被接受（`INSERT 0 2`，sum=10000），只插 9000 被拒 `revenue split total must equal 10000 basis points, got 9000`，探针全部回滚、残留 0 行。所以 G10 这条剩下的只是"拿真实结算单比对"，不是"补一套货币科目"。

### 待属主定值（不自行放宽安全控制）

1. **登录限流是按账号，且"拒绝也算一次"。** 先前本文写成"按 IP"是错的（那句 429 的症状被误读成按 IP）。读码 + 实测：键是 `login:sha256(email)`（`services/api/app/main.py:157`），第 11 次尝试起 429；随后每 30 秒试一次，连着 90 秒都进不去，直到**完全静默 75 秒**才恢复——因为 Lua 对每次 INCR 都无条件 `EXPIRE 60`，被拒的请求也会续期，窗口会随敲门的频率滑动。后果两面：同一出口 IP 的正常用户互不影响（原担忧不成立）；但任何人只要知道某个邮箱，就能持续把该账号挡在登录门外（无验证码、无 IP 维度），而对多账号分散撞库没有任何总闸。修法只需一行（只在 `n == 1` 时 `EXPIRE`，变成真正的固定窗口），但那是在改一条认证侧的安全控制，留给属主定夺；本轮只把**测试客户端**的退避改成实测可恢复的 75 秒以上（含 `browser_a11y.py` 与 `e2e_client.py`），没有动服务端缺省值。
2. **导航在 boot 完成前点了没反应。** `#app` 去掉 `hidden` 早于 `bindNavigation()`（它在首屏数据加载完之后才绑），所以首屏刚出来点顶栏按钮会被静默丢弃。验收脚本用"重试直到视图真的切换"绕过，但用户在慢网络下点到的就是没反应的按钮——要么把事件绑定提前到 DOMContentLoaded，要么在绑定完成前给出禁用态。
3. **两个前端共用一条会话 Cookie。** `localhost:4173` 与 `:4174` 同主机不同端口，Cookie 不分端口，所以 Studio 点"退出"会连带把管理后台会话一起作废（脚本里表现为后台首屏 401 留痕）。生产若把控制面放到同主机的另一端口，这就是一个真实的联动；需要域或路径隔离才算定案。
4. **匿名首屏把预期内的 401 记成 console error。**（本轮已修）`init()` 里 `/api/auth/me` 未登录时返回 401 属正常流程，却被 `console.error` 记录（上一轮 16 条 console 留痕里除了 CSP 全是它），两个应用都这么做；而 `admin.js` 的 `api()` 抛错时根本没挂状态码，所以那里就算写了按状态判断的守卫也判不出来。现在两处都只在非 401 时记错误，`api()` 挂上 `e.status`，门禁的 console 留痕 16 → 8 条，剩下 8 条是浏览器网络层自己记的 401（应用代码抑制不掉），`console.error` 一侧归零，常驻用例同时钉住「每个 `console.error` 调用点都必须带 401 守卫」与「状态码确实被挂上」。另记一条同族发现：Cookie 是按 host 而非按端口共享的，被删除的探针留下的失效会话 Cookie 会被同一 context 里的管理端 Origin 继承，于是管理端首屏的 401 从「需要认证」变成「会话已撤销」——这是被测应用的真实行为，但属于两 Origin 同机同 context 的夹具噪声，且该 Cookie 是 HttpOnly（`main.py:152` `httponly=True`），只有走查能清，走查于是清掉它。
5. **axe 还有 52 项 moderate**（权威运行实测分布：`heading-order` 36、`landmark-one-main` 8、`region` 8。上一版本文记的是 96 项 / `region` 56，其中 48 项 `region` 是「登录页在已登录视图上仍渲染」投下的影子——见附带发现第 16 条，修掉之后这条后续项的规模本身缩小了近一半，且剩下的 `region` 全部落在登录页自己身上），未达本 Gate 的判据线（critical/serious），但属于 WCAG 可达性问题，排后续轮次。
6. **删除权与 Legal Hold 的先后关系要谁定。** 法律保留在本仓库是真实生效的机制：`moderation_cases.legal_hold`（`db/migrations/002_creation_asset_market_os.sql:122`）会挡住市场上架（同文件 :568）、offer 创建（:680）与品牌中标（`004_brand_award_commercial_flow.sql:25`、`009_prepare_brand_award_ambiguous_column.sql:26`），对 project 开保留还会把状态改成 `legal_hold`（`services/api/app/routers/assets.py:247-248`）。但 `erase_user_identity` 完全不看这些：一个自己的 project 正被保留调查的主体仍可自助删除并被假名化。GDPR Art.17(3)(e)（为法律主张而保留）是否要在自助通道里落地、以及"谁的保留算数"（保留由员工 `opened_by` 开立，与被删主体往往不是同一人），是法务/产品判断而不是代码缺口；本轮只把它连同可核验的路径写清楚，不替属主装一条猜出来的守卫。
